## 3. 원인 A — TLS handshake 실패

### 증상

`dept.sejong.ac.kr`, `sw.sejong.ac.kr`, `pr.sejong.ac.kr` 세 서브도메인에 대해 파이썬에서만 `SSLV3_ALERT_HANDSHAKE_FAILURE` 발생. 정작 `curl`과 `openssl s_client`로는 `TLSv1.2 / AES256-SHA`로 정상 접속.

### 오진단과 정정 (중요)

처음에는 **"OpenSSL 3.x의 기본 보안 레벨(SECLEVEL=2)이 구형 스위트를 거부한다"**로 판단하고 `ctx.set_ciphers('DEFAULT@SECLEVEL=1')`로 보안 레벨을 통째로 낮췄다(`0412d28`). 동작은 했다.

그러나 직접 확인해보니 이 진단은 **틀렸다**:

```
openssl ciphers -v 'DEFAULT@SECLEVEL=2'   # → AES256-SHA 가 목록에 포함되어 있음
```

SECLEVEL=2에서도 `AES256-SHA`는 허용된다. 즉 OpenSSL의 보안 레벨은 애초에 원인이 아니었고, `SECLEVEL=1`은 **증상은 없애지만 이유가 틀린 처방**이었다.

### 진짜 원인

CPython이 `ssl.create_default_context()`에서 자체적으로 **하드코딩된 17개 스위트만 허용**한다. 이 목록은 forward secrecy가 있는 ECDHE/GCM/ChaCha 계열만 담고 있고, static-RSA 키교환 스위트인 `AES256-SHA`는 정책적으로 배제한다.

반대편 서버는 응답 헤더에 `X-ORACLE-DMS-*`가 찍히는 Oracle Fusion Middleware 계열 구형 스택으로, **ECDHE를 아예 지원하지 않고** `AES256-SHA` 같은 static-RSA 스위트만 제공한다.

→ 양쪽 허용 목록의 **교집합이 공집합**이라 handshake가 성립하지 않는다. `curl`은 OpenSSL 기본 목록(static-RSA 포함)을 쓰기 때문에 성공했던 것이고, 이 차이가 "브라우저·curl은 되는데 봇만 안 된다"의 정체였다.

### 대안 비교

| 안 | 방법 | 결과 |
|---|---|---|
| ① | `DEFAULT@SECLEVEL=1`로 보안 레벨 하향 | 작동하지만 필요 이상으로 넓게 허용. 진단도 틀림 |
| ② | forward secrecy는 유지하고 SHA1 MAC만 허용 (`ECDHE-RSA-AES256-SHA`) | **실패.** 서버가 ECDHE 자체를 지원하지 않아 무의미 |
| ③ | 파이썬 기본 17개는 그대로 두고 `AES256-SHA` 하나만 추가 | **성공.** 최소 범위로 해결 → 채택 (`45f992e`) |

### 최종 수정 — `bot/fetchers.py`

```python
class LegacyCipherAdapter(HTTPAdapter):
    def init_poolmanager(self, *args, **kwargs):
        ctx = ssl.create_default_context()
        default_ciphers = ':'.join(c['name'] for c in ctx.get_ciphers())
        ctx.set_ciphers(default_ciphers + ':AES256-SHA')
        kwargs['ssl_context'] = ctx
        return super().init_poolmanager(*args, **kwargs)


_session = requests.Session()
_session.mount('https://', LegacyCipherAdapter())
```

모든 fetcher가 `requests.get` 대신 이 `_session.get`을 쓰도록 교체했다.

> **주의**: 이 어댑터는 forward secrecy가 없는 스위트를 하나 되살린다. 공개 게시판 읽기 전용이라 감수한 트레이드오프이며, 인증 정보를 주고받는 요청에는 쓰지 말 것.

## 4. 원인 B — 파서 불일치

TLS를 고쳐 접속이 되기 시작하자, 그제서야 드러난 두 번째 층의 문제.

| 게시판 | 문제 | 수정 |
|---|---|---|
| 컴공 학부 | 5열(번호/**분류**/제목/등록일/조회수) 구조인데 기본 파서가 `cols[1]`에서 제목 링크를 찾음. `cols[1]`은 링크 없는 분류 컬럼이라 전 행 스킵 → **0건** | 동일 구조를 쓰는 `dept5` 파서 적용 |
| SW중심대학 | 4열(번호/제목/날짜/조회수) 구조인데 기본 파서가 5열 기준이라 **조회수 컬럼을 날짜로** 읽음 | 기존 `cedpt_intro` 파서 재사용 + `articleLimit` 쿼리 추가 |
| 국립국제교육원 | 사이트 리뉴얼로 `table tbody tr` → `ul.board-list > li` 구조로 개편. 기존 파서가 행을 못 찾음 | `a.tit`(제목) / `span.date`(등록일) 기준으로 재작성 |

여기서 특히 **컴공 학부**가 위험한 유형이었다. HTTP 200 + 파싱 0건이라 예외조차 나지 않아 로그에 `ERROR` 한 줄도 남지 않았고, `seen_ids | current_ids` 합집합 저장 때문에 `state.json`도 그대로 유지되어 **완벽하게 정상으로 보였다.**

## 5. 원인 C — 전역 `is_first_run`과 2차 사고

### 무슨 일이 있었나

2026-08-28T05:33Z, A/B 수정을 검증하려고 워크플로를 `workflow_dispatch`로 수동 실행했다. 그 결과 그때까지 `state.json`에 키가 없던 게시판들의 **누적 공지가 전부 "신규"로 판정되어 Slack에 발송**됐다.

```
2026-08-28T05:33:53Z  workflow_dispatch  success  production
2026-08-28T05:34:50Z  chore: update notice state [skip ci]   ← 397d7a3, 키가 한꺼번에 생김
```

컴공 취업뉴스 10건, 컴공 공모전 10건, AI·DS 학부 11건, 소웨학부 13건. 위 표에서 `–`가 숫자로 바뀐 그 순간이다.

### 원인

```python
is_first_run = len(current_state) == 0   # 전역 판정
...
if not is_first_run:
    new_notices = [n for n in notices if n['id'] not in seen_ids]
    ...send_slack(...)
else:
    ...  # 조용히 baseline만 저장
```

"첫 실행이면 알림 없이 baseline만 저장한다"는 보호 장치가 **`state.json` 전체가 비었을 때만** 동작한다. 기존 게시판이 하나라도 있으면 `is_first_run`은 `False`이고, 그러면 **새로 추가된 게시판**이나 **여태 한 번도 성공 못 한 게시판**도 곧바로 비교 경로를 타서 전체가 신규로 발송된다.

이 버그는 원인 A/B가 존재하는 동안에는 드러나지 않는다. A/B를 고치는 순간 트리거된다는 점에서, **수정 행위 자체가 방아쇠**였다.

### 수정 — `main.py`

```python
is_new_board = name not in current_state   # 게시판별 판정
...
if not is_new_board:
    ...  # 정상 비교 및 알림
else:
    print(f'{len(notices)} notices saved (new board)')
```

완전 첫 실행과 부분적 신규 게시판이 동일한 경로로 조용히 baseline만 저장하게 된다.

## 6. 왜 이렇게 오래 발견되지 않았나

가장 중요한 교훈은 개별 버그가 아니라 **실패가 보이지 않았다는 점**이다.

1. **게시판별 실패가 삼켜진다.** `main.py`의 루프는 `except Exception as e: print(f'ERROR: {e}'); continue`로 처리한다. 실패해도 다음 게시판으로 넘어가고, 워크플로는 **성공(success)으로 끝난다.** 워크플로 실행 이력에서 2개월간 모든 run이 `success`였던 이유다.
2. **에러가 Slack으로 안 간다.** 알림 채널에는 "새 공지"와 "업데이트 없음"만 나간다. 수집 실패는 GitHub Actions 로그를 직접 열어봐야만 보인다.
3. **0건 파싱은 에러조차 아니다.** 원인 B의 컴공 학부처럼 예외 없이 0건이면 로그에도 안 남는다.
4. **합집합 저장이 정지 상태를 숨긴다.** `seen_ids | current_ids`는 값을 절대 줄이지 않으므로, `state.json`만 봐서는 "조용한 게시판"과 "죽은 게시판"이 구분되지 않는다.

결국 2개월 가까이 아무 신호 없이 방치되다가, **사람의 신고**로 발견됐다.

## 8. 후속 과제

원인 3가지는 모두 수정됐으나, **6절의 관측 부재는 그대로 남아 있다.**

- [ ] 게시판별 수집 실패를 Slack으로 알리기 (연속 N회 실패 시 등)
- [ ] "HTTP 200인데 0건" 케이스를 실패로 취급 — 파서 불일치는 이 신호로만 잡힌다
- [ ] 전 게시판 실패 시 워크플로 자체를 실패 처리 (현재는 항상 success)
- [ ] `state.json`에 게시판별 마지막 성공 시각 기록 → 정지 상태 감지
- [ ] `config.BOARDS`에 게시판을 추가한 뒤 첫 실행이 실제로 성공했는지 확인하는 절차

미결 확인 사항: **위비티 공모전**은 현재도 `state.json`에 키가 없다. 원인 C 수정 덕분에 다음 실행에서 조용히 baseline만 저장되겠지만, **왜 여태 한 번도 성공하지 못했는지는 아직 조사되지 않았다.**
